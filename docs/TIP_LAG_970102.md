- `datum_last_accepted_share_tsms` updates **only on ACCEPT**
- REJECT does **not** refresh the timer
- Watchdog: if local shares sent and no ACCEPT for ≥30s → **kill protocol thread + reconnect**

#970218 timeline:

| Time | What |
|------|------|
| 13:11:31 | last **ACCEPT** |
| 13:11:32–13:12:01 | flood of **REJECT 27** (empty) — Prime *was* responding |

**Fix direction (GW):** treat any share *response* (accept **or** reject) as liveness; or pause
the watchdog during tip/empty grace; do not reconnect on reject storms.

### Architecture: one SV1 GW ≠ N× Prime load

**How coinbaser works on this gateway (convoy-pr10):**

- ~20–36 stratum miners share **one** current stratum job.
- **One** `datum_coinbaser_thread` watches `need_coinbaser` on the latest job.
- On need: **one** `0x10` to Prime → wait ≤15s → on ≥2 outs, `generate_coinbase_txns_for_stratum_job` once → all miners use that job’s multi-out.
- Miners do **not** each open a Prime coinbaser request.

So this SV1 GW is the **same shape** as any normal DATUM GW→Prime (1 fetch per job), **not** X× busier because of miner count. A separate “feeder” is not the right fix for scale.

**What *is* different / noisy:**

- Lots of short stratum connect churn (health checks / flaky clients) — does not multiply `0x10`.
- Prime also serves **other** DATUM GWs (e.g. `79.127…` reconnect storm, direct miner GWs) — ~50–80 `0x11`/min total. Our stuck SV1 only retries ~4 `0x10`/min (15s timeout loop).

**Stuck loop (still live after #970218):** job stays `ncb=1` → `Job N needs a coinbaser` → 15s timeout → retry → never `Generated`. `cbreuse` correctly silent across tip (no “reusing last good”). That is the critical bug: **live 0x10/0x11 for this session is dead**; reuse is only a same-tip bandage until the next tip.
